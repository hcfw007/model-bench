# l2-07：Rootless Podman 隔离

正式 `l2-07` 仅接受通过本机预检的 Linux rootless Podman 5.x。不会安装 Podman、拉取镜像、调用 `sudo` 或启动 root runner。macOS、未安装和不兼容部署仍可非 root 普通试跑；试跑标记 `isolation: "unverified"`，不得发布。

## 预先部署

由宿主运营方预先提供本机 rootless Podman、OCI runtime、用户命名空间支持及固定镜像；不要使用 remote Podman。宿主 runner 及交付服务均是普通非 root 进程。容器只运行 `l2-07` 的模型 CLI，不运行宿主 Git、判据或结果写入。选择支持绑定单个 Unix socket、OCI inspect 和私有命名空间的部署；额外默认挂载或不兼容 SELinux 策略会让预检拒绝，不会关闭安全选项。

- 镜像必须已在 rootless 本地存储，以仓库 manifest digest 和 image ID 双重锁定。镜像内需有配置的 OpenCode 程序、`/usr/bin/curl`、带 `node:sqlite` 的 `/usr/bin/node`，并支持读写 `/work` 和 `/model-home`。程序版本输出须与配置一致。镜像是受信输入，冻结前应由运营方审查。
- 为每个模型预置专属、权限 0700 的 HOME，由宿主 runner UID 持有，不能与业务仓库、控制器、其他模型目录、宿主 HOME 或结果目录重叠。放置 OpenCode 所需配置，使用 `/model-home/.local/share/opencode/opencode.db`。不要把宿主代理 socket、工具认证文件或宿主凭据目录放到模型 HOME。正式测评之间不得并行复用同一个模型 HOME。
- 容器网络固定为 `none`。交付 API 只通过只读绑定的 `/run/model-bench-delivery.sock` 对外开放。服务控制和审计使用宿主父进程管道，不映射。需要远程模型时，配置 `providerSocket`：这是运营方预先部署的仅转发允许的模型供应商请求的专用 Unix socket，所在路径不可由 runner 或模型替换；禁止通用代理、任意 CONNECT、内网访问和控制 API。镜像须能用 `/run/model-bench-provider.sock` 连接该代理；代理实现/供应商凭据不由 benchmark 部署。无代理仍可做无模型预检，不能假定普通需要互联网的模型可跑正式用例。
- `--privileged`、共享宿主网络/PID/IPC、额外 capabilities、设备、默认 host bind mount 都不允许。启动使用 `--pull=never`、只读根文件系统和 `no-new-privileges`；初始化后校验 Podman inspect 和 OCI spec，再运行镜像程序。结束后复核 inspect 并移除容器；超时也回收。
- 信任边界是被检查的 `l2-07` 模型容器，不是宿主上任意同 UID 的进程。受信宿主不得让无沙箱的其他模型任务以同一宿主 UID 并行运行；正式调度应使用专用普通 runner 身份或保证宿主任务不重叠且已回收。部署还须保护宿主 Podman 存储和协议产物；容器探针不承诺替代宿主作业调度。

配置文件和 Podman 二进制必须使用 root 所有、不可被组或其他用户写入的规范绝对路径，不能经过符号链接。这是受信部署输入，不是把 runner 当 root 启动。示例（用部署实际 digest/ID 替换）：

```json
{
  "podman": "/usr/bin/podman",
  "image": "registry.example.org/bench/opencode@sha256:REPLACE_WITH_MANIFEST_DIGEST",
  "imageId": "sha256:REPLACE_WITH_IMAGE_ID",
  "program": "/usr/bin/opencode",
  "version": "1.2.3",
  "modelHomes": {
    "openai/gpt-6.2-sol": "/home/bench/model-homes/sol"
  }
}
```

## 在已部署 Linux 上做无模型预检

以普通 runner 账户在仓库根目录运行：

```sh
node --input-type=module -e '
  import { verifyScenarioIsolation } from "./runners/lib/scenarios.ts";
  const { preflight } = verifyScenarioIsolation(process.argv[1], process.argv[2]);
  console.log(JSON.stringify(preflight, null, 2));
' /etc/model-bench/podman.json openai/gpt-6.2-sol
```

这会实际调用 Podman、从镜像运行 `curl` 检查公共 socket，再检查固定程序的 `--version`；不调用模型。预检失败时不要用环境变量或只改 JSON 放行，检查 Podman 行为、OCI 配置、精确挂载及镜像版本。本次开发主机未安装 Podman，已验证离线正反例，**未完成 Linux 实机预检**。

## runner / 协议接口

1. `verifyScenarioIsolation(configPath, modelId)` 返回 `{ config, preflight }`。正式运行在做任何模型工作前预检；冻结 `preflight.isolationId` 和根模式 `rootless-podman-v1`，保存每模型实际 `preflight`。隔离 ID 覆盖配置文件和宿主 Podman 程序字节；镜像、模型程序版本和 Podman 版本在证明中单列。宿主用于其余题目的 CLI 照原协议冻结。
2. `isolatedWorkspace(config)` 返回 `{ cwd, home, dbPath, close }`。以 `startScenario('l2-07', cwd, { formal: true, isolation: config })` 启动宿主权威端，只将 `scenario.publicSocket` 传给容器执行器。确保在容器退出后清理场景与工作区。试跑不传隔离配置。
3. 每轮用 `runIsolatedModel(config, workspace, scenario.publicSocket, 原OpenCode参数, { timeoutMs })`，得到 `{ child, proof }`。`child` 是标准 `SpawnSyncReturns<string>`；`proof` 来自容器初始化/结束前后的宿主检查。调用 `scenario.checkpoint(turn, trace, proof)`；证明留在 `checkpoints[].scenario.isolation`。没有证明的成功执行不计作普通断言失败，映射到 `missing_evidence`。
4. 发布端用 `scenarioPublicationBlocker(caseId, preflight, checkpoints.map(c => c.scenario), minimumCheckpoints)` 校验协议和逐轮证明。正常结算至少两轮，已证实首轮超时至少一轮；必须有匹配预检、不同容器 ID 和一致的工作区/公共端点。发布 agent 要读取宿主生成、模型不可写的正式产物；离线证明结构本身不能证明任意来源的 JSON 真实。
